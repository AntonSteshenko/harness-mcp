# Tasks: Local Self-Hosted S3 Storage

**Input**: Design documents from `/specs/001-s3-self-hosted-storage/`

**Prerequisites**: plan.md, spec.md, research.md, data-model.md, contracts/, quickstart.md (all present)

**Tests**: Not requested in the feature specification. This feature is Docker Compose configuration around the pre-built, upstream-tested `minio/minio` / `minio/mc` images (no custom application code), so verification is done via the `quickstart.md` scripted walkthrough rather than a unit/contract test suite (see research.md §6). Each user story phase below ends with quickstart-execution tasks that serve as its acceptance check.

**Organization**: Tasks are grouped by user story to enable independent implementation and testing of each story.

## Format: `[ID] [P?] [Story] Description`

- **[P]**: Can run in parallel (different files, no dependencies)
- **[Story]**: Which user story this task belongs to (e.g., US1, US2, US3)
- Include exact file paths in descriptions

## Dependencies & Execution Order

### Phase Dependencies

- **Setup (Phase 1)**: No dependencies - can start immediately
- **Foundational (Phase 2)**: Depends on Setup completion - BLOCKS all user stories
- **User Stories (Phase 3-5)**: All depend on Foundational phase completion
  - User stories can then proceed in parallel (if staffed)
  - Or sequentially in priority order (P1 → P2 → P3), which is recommended here since Phase 4's `createbuckets` service builds on the `minio` service healthcheck added in Phase 2/3, and Phase 5's volume touches the same `minio` service block edited in Phases 2–4
- **Polish (Phase 6)**: Depends on all three user stories being complete

### User Story Dependencies

- **User Story 1 (P1)**: Can start after Foundational (Phase 2) - no dependencies on other stories
- **User Story 2 (P2)**: Can start after Foundational (Phase 2) - independently testable via default buckets + CRUD, though in practice edits the same `docker-compose.yml` block as US1
- **User Story 3 (P3)**: Can start after Foundational (Phase 2) - independently testable via restart/reset, though in practice edits the same `docker-compose.yml` block as US1/US2

### Within Each User Story

- Implementation before validation
- `docker-compose.yml` edits before running any quickstart validation step
- Story complete before moving to next priority

### Parallel Opportunities

- T002 (README stub) can run in parallel with T001 (different file)
- T007 (`.env.example`) can run in parallel with T003–T006 (different file)
- T018 (`scripts/reset-storage.sh`) can run in parallel with T017 (different file)
- Because Phases 2–5 all converge on edits to the single `docker-compose.yml` file, most implementation tasks within those phases are sequential rather than parallel; the real parallelism in this feature is across file boundaries (compose file vs. `.env.example` vs. `scripts/` vs. `README.md`), not across user stories

## Implementation Strategy

### MVP First (User Story 1 Only)

1. Complete Phase 1: Setup
2. Complete Phase 2: Foundational (CRITICAL - blocks all stories)
3. Complete Phase 3: User Story 1
4. **STOP and VALIDATE**: Run quickstart.md Steps 1, 6, 7 independently

### Incremental Delivery

1. Complete Setup + Foundational → `minio` service ready
2. Add User Story 1 → validate independently → developers can start/stop the service (MVP!)
3. Add User Story 2 → validate independently → default buckets + full object CRUD
4. Add User Story 3 → validate independently → persistence + fast reset
5. Each story adds value without breaking previous stories, since all three build additively on the same `minio` service block
